Our Architectural Journey

How We Built It

Phase 01 — Zero-Hallucination Pricing

Pydantic Margin Guardrails

Every price the AI agent negotiates is validated through a PaymentProposal Pydantic model before any payment link is created. Floor prices are mathematically invariant — no prompt engineering can breach them.

floor_price ≤ agreed_price ≤ retail_price
Pydantic v2 Zero-Hallucination Margin Safety
Phase 02 — Multi-Turn State Engine

LangGraph State Machine & Razorpay Sandbox Rails

A directed acyclic graph orchestrates the conversation across three sales-psychology stages: Stage 1 opens with craftsmanship & a 4% goodwill discount, Stage 2 counters with the arithmetic retail-floor midpoint, Stage 3 closes only on verified buyer intent — then emits [ACTION:CREATE_PAYMENT] which triggers Razorpay SDK.

Stage 1 → Stage 2 → Stage 3 → [ACTION:CREATE_PAYMENT] → Razorpay SDK
LangGraph Google Gemini Razorpay SDK
Phase 03 — Cryptographic Settlement

HMAC-SHA256 Signature Verification & Immutable Audit Trail

Every Razorpay webhook is verified with a keyed HMAC-SHA256 signature. Forged or tampered payloads are rejected (HTTP 400) before any order state mutation — creating an immutable, append-only ledger. The computed signature is displayed in the Merchant HUD for real-time transparency.

HMAC = SHA256(raw_body, RAZORPAY_WEBHOOK_SECRET)
HMAC-SHA256 Immutable Ledger Tamper-Proof
Phase 04 — Drop-Off Re-engagement

Autonomous Failure Recovery & Re-engagement

When a payment_link.failed event is received (e.g. bank timeout, BAD_REQUEST_PAYMENT_TIMED_OUT), the agent's failure recovery node injects a warm, empathetic message explaining the error and generates a fresh 1-click payment link — retaining the original negotiated price.

FAILED → Recovery Node → Warm Message → Fresh Payment Link
Failure Recovery Auto Re-engagement Session-Aware
